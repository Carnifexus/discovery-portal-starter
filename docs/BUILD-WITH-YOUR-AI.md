# Prompt to paste into your AI coding assistant

> Help me build and verify a private discovery portal for my own firm. Use this repository and wholly invented material. Do not use an existing firm's workspace, case records, deployments, accounts, or secrets. No access change, external invitations, publication, or purchases without my approval. The respondent workflow must run without a model. A real deployment and this starter are separate.

## Follow this order

1. **Inventory this exact revision.** Identify the loopback demo, any deployable runtime, example intake, scanner interface, and available tests. Report the revision and which pieces are implemented versus reference designs. Start with the supplied fictional intake. Do not turn the loopback-only demo into a public server.
2. **Prove the workflow locally before choosing hosting.** Use separate counsel and respondent sessions. Import one ROG, one RPD, and one RFA. Confirm the original text and definitions, compare each plain-language explanation, and test assignment isolation. Answer the RFA first and leave the ROG unanswered. Attach a sample under the ROG, then answer without a file requirement. Use the RPD actions for searching, not kept, never existed, cannot find, and ask counsel for help. Confirm that the answer persisted and counsel can see it.
3. **Set up one private staging target.** Use the [Azure reference](AZURE-SETUP.md) or document an equivalent. Separate hosting resources from application data. Set the exact HTTPS origin, restrict network and sign-in, scope the managed identity to required containers, authorize the independent scanner separately, and keep keys out of the repository. Set a cost limit or alert, not a new paid platform by default.
4. **Package and deploy only the runtime.** Keep a file allowlist; host.json and the entry point go at the package root for Azure Functions. Check archive entry permissions for non-root Linux use. Confirm the function actually responds over HTTPS; do not equate an upload receipt with a running function. Test a completely new browser session, including refresh, and inspect whether the cookies the browser actually received retain the security properties that the application set. If the host rewrites cookies, fix the platform adapter or choose a documented staging-specific solution; never switch off secure cookies, CSRF, or access restrictions to make a test pass.
5. **Check failure as well as success.** Stop or disconnect the scanner and verify that no pending file becomes downloadable. Bring it back, scan an invented file, and compare the cleared download with the original digest. Test second-respondent and second-matter isolation, sign-out and revocation, retrying an accepted submission, and restoration into a separate private environment. Compare the saved answers and encrypted objects after restore and prevent old sessions or revoked access from coming back.
6. **Write a handoff the lawyer can use.** Record only sanitized test evidence, application and release versions, instructions for preparing and checking assignments, how to operate the scanner, how to revoke someone, and how to recover. List exactly what did not pass. Do not call it ready for client data until the operator reviews the actual platform, participant roles, privacy terms, and test results. Do not send, file, serve, or make final responses automatically.

If asked to add AI to the application, treat it as a separate, disabled-by-default counsel workflow. Use invented or public text initially; show the lawyer exactly what is to be transmitted. Do not give a model direct client portal, scanner, or storage access. Confirm endpoint, approved use, region, retention and disclosures against the vendor's current terms before any confidential input. The portal itself does not need AI to receive answers or documents.
